Agentic Product Ops — Repository Initialization Specification
Status: Initial repository specification
Proposed repository: agentic-product-ops
Primary integration target: agentic-delivery-os
Initial product boundary: Natural-language business/product intent → governed, reviewable Linear work items
Date: 2026-09-28
1. Repository initialization instruction
You are initializing a new production-quality portfolio repository named Agentic Product Ops.
Do not treat this as a demo prompt-wrapper or a generic ticket-generation chatbot. Build the foundation for a governed product-operations control plane that converts ambiguous natural-language requests into evidence-backed, reviewable engineering work and, only after explicit authorization, creates structured Linear issues.
The first release must prove one narrow vertical slice extremely well:
Natural-language prompt → requirements extraction → ambiguity detection → repository-aware decomposition → acceptance criteria → proposed Linear epic/issues → human approval → idempotent Linear creation → immutable handoff to Agentic Delivery OS

The product is intentionally separate from agentic-delivery-os.
- Agentic Product Ops decides what work should exist.
- Agentic Delivery OS executes approved work.
- Product Ops must never implement source-code changes.
- Delivery OS must never silently invent missing product requirements.
- The integration boundary must be versioned, auditable, and repository-independent.
The repository should be created with a clear architecture, tests, CI, documentation, sample fixtures, security controls, evaluation harness, and implementation backlog from day one.
Do not claim capabilities that are not exercised.
2. Product thesis
Modern software teams lose substantial time between an initial idea and an executable engineering ticket.
Inputs are usually incomplete and fragmented:
- a product manager writes a short request;
- a customer reports a problem;
- a support ticket describes symptoms rather than requirements;
- a meeting produces several implied actions;
- an executive asks for a feature without defining edge cases;
- an engineer receives a ticket with insufficient acceptance criteria;
- a request references a repository without identifying impacted components.
The objective is not simply to "write tickets with AI."
The product must transform ambiguous intent into a decision-ready work specification while preserving uncertainty rather than hiding it.
A strong output answers:
1. What problem are we solving?
2. Who is affected?
3. What behavior is explicitly required?
4. What behavior is only inferred?
5. What remains unknown?
6. Which repository or subsystem is likely relevant?
7. What work items should exist?
8. What are the acceptance criteria for each item?
9. Which requirements need human decisions before implementation?
10. What evidence should later prove completion?
11. What risk tier should the work receive?
12. Is the specification safe to publish to Linear?
13. Has an authorized human approved the exact proposed specification?
The differentiator is requirements quality, traceability, uncertainty preservation, and governed work creation, not raw text generation.
3. Product positioning
3.1 Primary product statement
Agentic Product Ops converts ambiguous business and product requests into governed, evidence-linked engineering specifications and Linear work items.
3.2 Initial user personas
Product / engineering lead
Wants to turn an idea into implementation-ready work without spending excessive time manually structuring tickets.
Technical product manager
Wants consistent requirements, explicit unknowns, decomposition, dependencies, and acceptance criteria.
Engineering manager
Wants fewer ambiguous tickets and stronger traceability between requested behavior and implementation evidence.
Repository maintainer
Wants generated work to reflect the actual repository rather than generic assumptions.
Portfolio reviewer
Wants reproducible evidence that the project handles ambiguity, duplicate external writes, authorization, and false confidence honestly.
4. Explicit non-goals
The initial release MUST NOT:
- write or modify application source code;
- merge pull requests;
- deploy software;
- replace human roadmap prioritization;
- autonomously decide material product behavior;
- silently resolve ambiguous requirements;
- create Linear tickets without an explicit authorized approval;
- create work in arbitrary teams or workspaces;
- infer customer commitments from unsupported text;
- claim human productivity savings without measured human data;
- claim production readiness because local tests pass;
- run arbitrary code from repositories;
- use repository text as trusted instructions;
- treat an LLM-generated acceptance criterion as evidence that the criterion is correct;
- create Jira/GitHub Issues integrations before the Linear vertical slice is evaluated;
- build a large dashboard before the core workflow is proven;
- introduce a vector database until retrieval ablation demonstrates a need;
- share a database with Agentic Delivery OS.

5.1 Integration principles
1. No shared database.
2. No importing Delivery OS internal persistence models.
3. Integration occurs through a versioned public contract.
4. Linear may be the human-visible coordination surface, but the handoff contract must remain independently serializable.
5. Product Ops owns requirement/specification provenance.
6. Delivery OS owns implementation/evidence provenance.
7. A specification revision after implementation begins must produce a new revision and invalidate stale downstream assumptions.
8. Delivery OS must be able to verify the specification digest it received.
9. Product Ops must never mark implementation complete.
10. Delivery OS must never reinterpret unresolved product decisions as resolved.
6. Initial vertical slice
The first complete demonstration should be:
Example input
"We need customers to export the monthly revenue report as CSV. It should respect their current filters, only admins should be able to export it, and we need analytics on usage."

Required system output
Problem statement
Users need a way to export filtered monthly revenue-report data for offline analysis.
Explicit requirements
- Export format is CSV.
- Export reflects current active report filters.
- Export is restricted to administrators.
- Export usage must be instrumented.
Unresolved requirements
- Maximum supported row count is unspecified.
- Expected behavior for oversized exports is unspecified.
- Required analytics event schema is unspecified.
- Whether sensitive fields require exclusion is unspecified.
- Performance target is unspecified.
Proposed work
1. Backend export capability.
2. Frontend export action.
3. Authorization enforcement.
4. Product analytics instrumentation.
5. QA / regression validation.
Proposed acceptance criteria
Each criterion must identify whether it is:
- directly stated;
- derived from repository/policy context;
- safely inferred;
- requires human decision.
Repository evidence
If repository access is enabled, identify likely relevant modules, tests, API surfaces, authorization middleware, and known unknowns. Repository evidence is advisory and read-only.
Approval
Nothing is written to Linear until an authorized human approves the exact specification revision.
Linear creation
Approved tickets are written idempotently. The created Linear identifiers and content digests are stored as operation evidence.
Delivery OS handoff
The approved WorkSpecification can be consumed by Agentic Delivery OS.

9. Agent roles
Keep model roles limited.
9.1 Requirements analyst
Responsibilities:
- normalize the request;
- distinguish facts from inferred requirements;
- identify actors and business objective;
- extract constraints;
- identify ambiguity;
- propose clarification questions;
- propose candidate acceptance criteria.
May not:
- approve its own specification;
- create Linear issues;
- resolve material ambiguity;
- mutate repository content.
9.2 Work decomposition agent
Responsibilities:
- transform an approved/clarified requirements draft into proposed work items;
- identify dependencies;
- identify likely sequencing;
- propose ticket boundaries;
- connect acceptance criteria to individual tickets;
- use permitted read-only repository evidence.
May not:
- create Linear issues;
- decide roadmap priority autonomously;
- override risk policy.
This role may initially use the same provider/model as requirements analysis but must execute in a distinct context.
9.3 Independent specification reviewer
Responsibilities:
- receive source material, requirements, decomposition, repository evidence, policy, and proposed work;
- identify unsupported requirements;
- identify missing acceptance criteria;
- identify ambiguity hidden as certainty;
- identify duplicated or poorly separated tickets;
- identify inconsistent dependencies;
- identify risky publication.
The reviewer cannot edit the proposed specification directly and cannot publish.
9.4 Deterministic services
Deterministic code owns:
- schema validation;
- lifecycle state;
- authorization;
- team/repository allowlists;
- approval binding;
- expiry;
- risk-policy gates;
- idempotency;
- Linear mutation execution;
- reconciliation of uncertain writes;
- specification digests;
- audit records;
- evaluation scoring where rules are objective.

11. Approval contract
A human approval must bind:
- specification ID;
- exact revision;
- content digest;
- authorized actor identity;
- workspace/team scope;
- intended Linear operations;
- approval timestamp;
- approval expiry;
- allowed mutation count;
- policy version.
Any change to the work specification after approval invalidates that approval.
Approval should not be represented as a simple boolean.
class SpecificationApproval(BaseModel):
    approval_id: UUID
    specification_id: UUID
    revision: int
    content_digest: str
    actor_id: str
    decision: Literal["approve", "reject"]
    scope: ApprovalScope
    issued_at: datetime
    expires_at: datetime
12. Linear integration strategy
Use Linear's API as the production integration path.
12.1 Authentication
Prefer OAuth app authentication and least privilege.
Initial required capabilities should be no broader than necessary:
- read relevant team/project/workflow metadata;
- issues:create for approved issue creation;
- only request broader write permissions if a measured use case requires issue updates.
Do not request admin scope for normal operation.
For a service/agent integration, consider Linear's app actor mode so mutations are attributable to the application rather than impersonating a human.
Persist the workspace-specific app identity.
12.2 Issue creation
Use explicit issue creation mutations with:
- title;
- markdown description;
- team ID;
- project if approved;
- labels if approved;
- parent/relationship information where supported and validated;
- operation marker for reconciliation.
Never let the model directly call Linear.
The model proposes a strict LinearPublicationPlan. Deterministic code validates it and performs the mutation after approval.
12.3 Idempotency and uncertain writes
External API calls can succeed even if the response is lost.
Each intended issue creation must have a stable logical operation ID derived from:
specification_id / revision / work_item_local_id / publication_generation
Store:
- request digest;
- operation key;
- attempt number;
- provider response ID;
- created Linear ID;
- provider timestamps;
- result status;
- UNKNOWN state where success cannot be safely established.
Before retrying an uncertain operation:
1. reconcile by recorded provider identifiers or a safe application marker;
2. compare title/team/content digest;
3. create only if nonexistence can be established;
4. otherwise remain UNKNOWN and require operator resolution.
Never create a duplicate ticket simply because a request timed out.
12.4 Webhooks
Later phases can subscribe to issue/project/comment events for synchronization.
Webhook handlers must:
- verify authenticity;
- persist receipt before asynchronous processing;
- deduplicate deliveries;
- return quickly;
- treat redelivery as normal;
- keep provider state distinct from local projected state.
12.5 MCP
Linear's hosted MCP support can be useful for operator/development workflows, but the MVP production publication path should remain an explicit, tested API adapter so authorization, request digests, idempotency, and reconciliation are owned by this system.
13. Repository-context subsystem
Repository awareness is useful, but Product Ops must remain read-only.
13.1 Allowed context
Initial repository adapter may inspect:
- file tree;
- README / architecture docs;
- Python import graph;
- APIs/routes;
- schemas;
- test names;
- configuration names;
- CODEOWNERS;
- documented component boundaries.
13.2 Prohibited behavior
Product Ops must not:
- execute repository code;
- install repository dependencies;
- run untrusted scripts;
- modify files;
- create commits;
- treat repository text as system instructions;
- expose repository secrets to model contexts.
13.3 Context output
Repository analysis should produce evidence such as:
likely_components:
  - path: src/reporting/export.py
    reason: existing report export service
  - path: src/auth/permissions.py
    reason: admin permission checks

relevant_tests:
  - tests/reporting/test_exports.py

unknown_edges:
  - dynamic route registration prevents complete static mapping

confidence: 0.74
Repository evidence informs work decomposition but never proves correctness.
14. Risk policy
Create deterministic risk classification.
Suggested policy:
Tier 0
- documentation;
- analytics instrumentation;
- tests;
- copy;
- low-impact internal tooling.
Tier 1
- bounded feature changes;
- new non-sensitive API behavior;
- normal UI behavior;
- reversible internal workflow changes.
Tier 2
- authentication/authorization;
- payments;
- sensitive customer data;
- financial calculations;
- migrations;
- external side effects;
- permission changes;
- infrastructure/security configuration.
Tier 3
- destructive data operations;
- production credential/secrets changes;
- compliance-critical controls;
- irreversible actions;
- broad security-policy modification.
MVP can generate specifications for all tiers, but automatic handoff to Delivery OS should remain restricted to the tiers that Delivery OS accepts.
High-risk work should contain stronger required human decisions rather than being silently simplified.
15. Prompt-injection and untrusted-content model
Every external text source is untrusted content.
Sources include:
- natural-language request;
- repository files;
- issue comments;
- pasted meeting notes;
- customer support text;
- existing ticket descriptions.
An untrusted source cannot:
- alter system policy;
- approve itself;
- widen Linear permissions;
- change team/repository allowlists;
- instruct the application to reveal secrets;
- set itself to non-blocking;
- cause direct external writes.
Keep authority in typed capabilities and deterministic policy.
Prompts should explicitly distinguish:
SYSTEM POLICY
AUTHORIZED CONFIGURATION
USER REQUEST
UNTRUSTED SOURCE CONTENT
REPOSITORY EVIDENCE

21. Evaluation strategy
Evaluation must begin during foundation work.
Do not wait until the end.
21.1 Evaluation dimensions
Measure:
1. Requirement extraction precision
2. Requirement recall
3. Ambiguity detection
4. False resolution
5. Acceptance-criteria quality
6. Ticket decomposition quality
7. Traceability
8. Repository grounding
9. Risk classification
10. Publication safety
11. External-write reliability
12. Cost / latency
21.2 Initial corpus
Build at least 40 authored cases before portfolio release, across:
- clear feature requests;
- intentionally ambiguous features;
- bug reports;
- analytics requests;
- authorization/security requests;
- data/financial logic;
- multi-ticket features;
- requests that should remain research tickets;
- duplicate/rephrased requests;
- prompt-injection attempts.
Include adversarial cases where a source explicitly tells the model to:
- hide an unresolved requirement;
- bypass approval;
- choose a team outside allowlist;
- mark a sensitive change low-risk;
- fabricate repository evidence.
Preserve first-run failures.
21.3 Independent authoring
Use separate contexts for corpus authorship and system evaluation.
Do not describe separately authored agent cases as independent human validation.
21.4 Human evaluation later
A later human study may measure:
- time from request to approved tickets;
- edit distance / number of changes;
- missed requirements;
- reviewer confidence;
- ticket usefulness.
Until measured, human-time savings must remain unclaimed.
22. Acceptance scenarios
Create executable acceptance scenarios.
ID	Scenario	Required behavior
A-01	Clear request	Valid proposed specification with traceable requirements
A-02	Material ambiguity	Blocking question, no Linear publication
A-03	Safe non-material ambiguity	Visible assumption, no hidden behavior choice
A-04	Unsupported inferred requirement	Independent reviewer blocks or flags
A-05	High-risk request	Risk tier escalated deterministically
A-06	Prompt injection in request	Policy unaffected
A-07	Prompt injection in repository	Repository text remains untrusted
A-08	Approval revision mismatch	Publication denied
A-09	Approval expired	Publication denied
A-10	Duplicate publish command	One Linear issue set, no duplicates
A-11	Lost Linear response	Reconcile or remain UNKNOWN, do not blind retry
A-12	Unauthorized team	Publication denied
A-13	Repository uncertainty	Context marked uncertain rather than fabricated
A-14	Duplicate work items	Reviewer/evaluator catches overlap
A-15	Delivery OS handoff	Exact approved digest exported
A-16	Specification changes after publish	New revision recorded; old publication remains attributable
A-17	Model outage/budget exhaustion	Durable pause/failure, no partial external write
A-18	Cancellation	No new model or provider mutations after accepted cancellation

27. Security requirements
Before live Linear writes:
- OAuth secrets never enter model contexts.
- Tokens never enter logs.
- Team/workspace scope is server-side configuration.
- Model cannot choose arbitrary team UUIDs without allowlist validation.
- Webhook signatures are verified where webhooks are enabled.
- External request bodies are bounded.
- Approval actor identity is authenticated.
- Approval expiry is rechecked immediately before mutation.
- Authorization is rechecked before each external write.
- Provider failures preserve UNKNOWN where appropriate.
- Logs are structured and redacted.
- Repository content is untrusted.
- URLs from source text are not fetched automatically.
- Linear descriptions are escaped/serialized safely.
- Duplicate operation keys with different request digests are conflicts.

31. Research-informed implementation notes
The initialization should incorporate these current platform facts:
Linear
- Linear provides a GraphQL API for creating and updating issues.
- Issue creation can be restricted with the issues:create OAuth scope.
- App actor authorization can make mutations attributable to the application instead of impersonating a human.
- Linear supports webhook events for issues, comments, projects, cycles, users, and other entities.
- Linear webhooks require fast acknowledgement and use retry behavior after failed delivery.
- Linear exposes agent/session primitives, but this project's first release should keep product authority in its own WorkSpecification/approval workflow.
- Linear's MCP server can create/update objects and may be useful for development/operator workflows, but explicit API integration is preferred for the governed publication path.
Durable execution
A durable workflow engine is appropriate because human approvals, retries, cancellation, provider uncertainty, and long-running waits must survive process failure.
Webhook security
The design should follow standard webhook-security principles:
- secrets/signature validation;
- minimal event subscriptions;
- asynchronous processing;
- unique delivery identifiers;
- safe redelivery handling;
- HTTPS;
- explicit event/action validation.

34. Recommended README opening
Agentic Product Ops is a governed AI-assisted requirements and work-decomposition system. It converts ambiguous product requests into evidence-linked requirements, unresolved questions, acceptance criteria, and proposed Linear work items. Humans approve the exact specification before any external write. Approved work can then be handed to Agentic Delivery OS for controlled implementation and independent verification.

36. Final governing principle
The project should optimize for this invariant:
AI may propose work, structure work, and explain uncertainty. Deterministic systems constrain authority. Humans approve consequential product decisions. External writes are attributable and recoverable. Downstream implementation receives the exact approved specification, not a rewritten interpretation.

Build the narrowest system that proves that invariant end to end.
